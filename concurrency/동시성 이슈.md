

## 데이터 베이스 

여러 사용자가 동시에 제품을 구매할 때 재고가 충분하지 않은데도 재고 부족 오류가 발생하지 않음.
이유는 여러 트랜잭션이 동시에 재고 수를 읽고 갱신하면서 경쟁 조건이 발생하기 때문

### 이슈 재현
> Product 재고가 1000개 있는 상황에서 120개의 스레드가 동시에 10개씩 구매한다고 가정함. 
> 예상한 결과는 101번째부터 재고부족 현상이 떠야함.

@Slf4j  
@RequiredArgsConstructor  
@RestController  
public class TestController {  
    private final TestService testService;  
  
    @PutMapping("/products/{id}/purchase")  
	public void test(@PathVariable Long id) throws InterruptedException {  
	    long start = System.currentTimeMillis();  
	  
	    int threadCount = 120;  
	    ExecutorService executorService = Executors.newFixedThreadPool(threadCount);  
	    CountDownLatch latch = new CountDownLatch(threadCount);  
	  
	    for (int i = 0; i < threadCount; i++) {  
	        int finalI = i;  
	        executorService.submit(() -> {  
	            try {  
	                final int quantity = 10;  
	                testService.purchaseProduct(id, quantity, finalI);  
	            } finally {  
	                latch.countDown();  
	            }  
	        });  
	    }  
	  
	    latch.await();  
	    executorService.shutdown();  
	  
	    long end = System.currentTimeMillis();  
	    log.info("소요시간: {}ms", (end - start));  
	}
}


@Slf4j  
@RequiredArgsConstructor  
@Service  
public class TestService {  
    private final ProductJpaRepository productJpaRepository;  
  
    public void purchaseProduct(Long productId, int quantity, int index) {  
        log.info("({}번째) 상품 {}을(를) {}개 구매 시도", index, productId, quantity);  
        ProductEntity product = productJpaRepository.findById(productId).get();  
        if (product.getStock() >= quantity) {  
            product.setStock(product.getStock() - quantity);  
            productJpaRepository.save(product);  
        } else {  
            log.error("재고부족! {}번째 요청", index);  
            throw new InsufficientStockException(ResultCodes.P9999);  
        }  
    }  
}

@Setter  
@Getter  
@NoArgsConstructor(access = AccessLevel.PROTECTED)  
@Table(name = "products")  
@Entity  
public class ProductEntity {  
  
    @Id  
    @GeneratedValue(strategy = GenerationType.IDENTITY)  
    private Long id;  
  
    private Long userId;  
  
    private Long stock;  
  
    private LocalDateTime createdAt;  
  
    @Builder  
    public ProductEntity(Long id, Long userId, Long stock, LocalDateTime createdAt) {  
        this.id = id;  
        this.userId = userId;  
        this.stock = stock;  
        this.createdAt = createdAt;  
    }  
}

public interface ProductJpaRepository extends JpaRepository<ProductEntity, Long> {  
}

### 해결방법 후보
- `@Transactional` 를 건다.
	- 로직이 종료될 때까지 락을 걸어서 동일데이터를 업데이트하지 못하게 한다.
- `syncronized`를 건다.
	- 하나의 스레드만 접근할 수 있음
- 쿼리에 for update를 한다. 
	- 트랜잭션이 종료될 때까지 select 된 row들 모두 lock이 걸림

> 트랜잭션을 걸었을 때는 HikariCP에서 커넥션 풀을 통해 동일한 커넥션을 유지하고, Connection Pool로 병렬처리 수를 제한한다. 하지만 트랜잭션 애노테이션을 걸지 않으면 요청단위로 가져와서 반환하게 되어 독립적으로 실행하게 된다. 


> 결론은 Transactional 애노테이션은 병렬처리수를 제한하고, 트랜잭션으로 인해 로직간의 쓰기 롤백으로 일관성을 어느정도는 유지할 수 있지만 병렬처리 되는 스레드간에 동시에 같은 데이터를 읽었다면 여전히 해결되지 않는다. 


### 해결방법 후보
- `@Transactional` 를 건다. -> X (병렬처리 제한이 되어 보완은 되지만 해결은 되지 않음)
	- 로직이 종료될 때까지 락을 걸어서 동일데이터를 업데이트하지 못하게 한다. 
- `syncronized`를 건다.
	- 하나의 스레드만 접근할 수 있음
- 쿼리에 for update를 한다. 
	- 트랜잭션이 종료될 때까지 select 된 row들 모두 lock이 걸림


```java
@Slf4j  
@RequiredArgsConstructor  
@Service  
public class TestService {  
    private final ProductJpaRepository productJpaRepository;  
  
    public synchronized void purchaseProduct(Long productId, int quantity, int index) {  
        ProductEntity product = productJpaRepository.findById(productId).get();  
        log.info("({}번째) 상품 {}을(를) {}개 구매 시도. 잔여재고: {}", index, productId, quantity, (product.getStock() - quantity));  
        if (product.getStock() >= quantity) {  
            product.setStock(product.getStock() - quantity);  
            productJpaRepository.save(product);  
        } else {  
            log.error("재고부족! {}번째 요청", index);  
            throw new InsufficientStockException(ResultCodes.P9999);  
        }  
    }  
}
```
